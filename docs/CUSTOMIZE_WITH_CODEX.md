# Codexでカスタマイズする

## リポジトリ内の役割

### `AGENTS.md`

Codexが作業開始時に読むリポジトリ固有の規則です。事実性、既存データ保全、帰属表示、テスト、Git運用等を定めています。新しいCodexセッションを開始すると、ルートから作業場所までの指示が読み直されます。

### `DESIGN.md`

現行デザインの設計正本と、利用者の変更希望を書く場所です。このファイルを書くだけでは表示は変わりません。「21. デザイン変更指示」を編集し、Codexへ実装を依頼します。

### `assets/css/theme.css`

メインカラー、本文色、背景、フォント、主要余白、角丸、ヘッダー／ナビ寸法、アニメーション時間等を集約しています。横断的なデザイン変更は、まずここで対応します。

### `prompts/`

目的別の依頼文テンプレートです。各ファイルの入力欄を埋め、Markdown全体をCodexへ貼り付けます。リポジトリ内のこれらのファイルは、Codexのスラッシュコマンドや自動実行機能ではありません。

### `index.html`と`sample.html`

- `index.html`: 実際に公開する研究室情報を入力する正本
- `sample.html`: 完成見本、長文、空データ、件数境界、回帰試験用

両ページは同じCSS、JavaScript、画像を利用します。

## 目的別プロンプトの使い方

1. 今回の目的に合う`prompts/*.md`を開きます。
2. 入力欄へ確認済み情報を貼ります。
3. 不明な項目は「不明」または空欄にします。
4. プロンプト全体をCodexへ渡します。
5. Codexが作業前状態を確認したことを確認します。
6. 変更、テスト、commit、pushの報告を読みます。

複数の目的を一度に詰め込まず、NEWS、メンバー、論文、デザイン等を分けると、commit単位で確認しやすくなります。

## Codexの報告の読み方

- **結論**: 依頼が受入条件を満たしたか
- **変更内容**: 利用者から見た表示・操作の変化
- **テスト**: 実施済み、失敗、未実施、検証不能の区別
- **変更ファイル**: どこが変更されたか
- **commit**: 変更をまとめたGit上の記録番号
- **push**: remoteのGitHubへ送信されたか
- **残課題**: 今回完了に含まれない事項

「おおむね成功」ではなく、失敗や検証不能が明記されているか確認してください。

## 意図しない変更を元に戻す考え方

Gitのcommitは、変更を確認可能な単位で保存します。意図しない結果があった場合は、対象commitと戻したい内容をCodexへ示し、安全な打ち消し変更を依頼してください。

未コミット変更がある状態で`reset --hard`、checkout、stash等を自己判断で実行しないでください。既存変更を失う可能性があります。

GitHubのcommit一覧では、commitごとの差分をブラウザで確認できます。1依頼1目的に近づけると、問題箇所を特定しやすくなります。

## デザイン変更

1. `DESIGN.md`の変更指示を編集します。
2. `prompts/APPLY_DESIGN.md`をCodexへ渡します。
3. Codexは`theme.css`を優先して変更します。
4. PC/SP、フォーカス、帰属表示、主要操作を確認します。
5. 現行仕様との差分を人が確認します。

大きく情報構造が異なる別デザインでは、HTML変更も必要になる場合があります。JavaScript機能と情報構造は可能な限り共有します。
